# CHANGELOG 條目

## 一條等於一個「使用者看得到的功能主題」

條目跟 commit 一樣，**動詞開頭、一行寫完**。但一條的粒度是「一個功能主題」，不是工程上的一個改動點。一個版本控制在 **15–20 條**。

**為什麼：** 兩次回饋疊加的結果。第一次被指出條目寫成五行長的名詞句很難讀，於是改成一個子功能一條，結果一版變成 27 條，再被說「精簡項目，太多了」。把同主題的條目併回之後，從 27 條變成 18 條，行數從 67 減到 46。「一條一件事」的「一件事」，指的是使用者感受得到的一件事。

**怎麼做：**

- 動詞對應分類：Added 用「新增」、Changed 用「調整」、Removed 用「移除」、Fixed 用「修復」。
- 同一功能的多個改動點用「；」接在同一條，不要拆成好幾條。
- 同一個根因的多個修補併成一條。
- 超過 20 條時，先找可以合併的同主題條目，不是刪內容。

## 哪些東西不寫進 CHANGELOG

| 不放 | 放哪裡 |
|------|--------|
| enum 常數名、資料表欄位名 | PR 說明 |
| 門檻數字（「15 分鐘 10 次」） | PR 說明或規格文件 |
| 完整的查詢語法、端點清單 | 技術文件 |
| `.env` key 逐條列出 | `.env.example`，加上檢查指令 |

可以放的：使用者看得到的名稱（頁面、按鈕、分類名稱）、指令名稱。

## 工程／部署專區

改成「部署依序：」加上編號步驟，例如：放行網路 → 檢查 env → migrate → seeder → 清快取並重建容器 → 驗證 → 回填資料。一步可以包含多個指令。

- 步驟之後最多三條補充，只寫步驟裡沒提到、而且部署時會用到的事。
- 沒有新 env／migration／權限的改動，就不用寫「無異動」。

## 發版

- 開發中的條目先放 `[Unreleased]`，發版時搬進版本段落，`[Unreleased]` 留下空標題。
- 版本日期在打 tag 時才填，在那之前先寫 `YYYY-MM-xx`。
