# 溝通：讓使用者用最少力氣做出判斷

## 先結論，後細節

回答第一段就給結論或建議，理由與細節放在後面。要權衡選項時直接給推薦，不要列出一份沒有立場的比較清單。

## 改動超過 3 個檔案，先說明計畫

動手前列出會改哪些檔案、每個檔案改什麼、有什麼需要使用者決定的事。使用者確認後再開始。單檔或小範圍修改不用。

## 要使用者決定的事，放在他看得到的地方

需要使用者拍板的事，必須出現在他實際會看的位置（對話結尾、看板卡片、PR 說明），寫成可以直接回答的選項，例如「問題：A) … B) …」，並附上他具體要做的下一步。

**為什麼：** 審查結果裡有一條需要決定的事，但只寫在審查檔裡，卡片上沒有任何選項。使用者表示，要不是主動追問，根本不知道有事要決定，也不知道該在哪裡回答。

**怎麼做：** 設計任何流程時都先問自己：使用者在他平常看的畫面上，看得到下一步嗎？

## 帶使用者操作不熟的 UI，要一步一步來

要使用者在 Kibana、雲端主控台、CI 平台這類不常用的介面操作時：

1. 給直達網址，不要寫「進到某某頁面」。
2. 每一步給一段可以整段貼上的指令，並說明在哪裡按執行、右邊預期會出現什麼。
3. 先做唯讀查詢並設檢查點（「做到第 N 步，把結果貼給我」），看過真實狀態後再給會改動東西的步驟。每個改動步驟都寫出預期的回應。
4. 用 `filter_path` 這類參數把輸出縮小，讓使用者貼回來的內容越短越好。
5. 事先列出可能卡住的狀況，例如權限不足時錯誤訊息長什麼樣子、替代的 UI 路徑。

**為什麼：** 一次丟出整份 runbook，使用者無法判斷哪一步出錯。分段加檢查點也讓 agent 能在改動前看到真實狀態。有一次就是靠使用者貼回來的查詢結果，才發現要動的資料被其他系統共用、不能刪。

## 命名提案要給整組，並附比較表

要替功能、畫面文字取名時，給 2–3 組完整的命名組合（功能名、模板名、單筆項目名一起給），每組附優缺點，讓使用者選。不要只給一個名字。

## 大範圍的變動，先小範圍示意

整理白板、重排版面、批次重新命名這類一次影響很多東西的操作，先改一小部分或畫一張示意給使用者看，確認方向後再擴大。

**為什麼：** 有一次只憑 API 座標，就把白板上十幾個框架整批搬到新區域重排，連續多次結果都不理想。框架跟原本的位置脫離，手動拉過轉折點的連接線也跑版了。agent 看不到實際畫面，只看座標就整批執行，結果一定會走樣。

**怎麼做：** 動手前記下原始狀態以便還原；能截圖就先看實際畫面；長距離搬移或結構性變動先提案，不要直接做。
