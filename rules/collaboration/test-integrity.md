# 測試完整性：不為了變綠而改測試

## 不刪、不跳過、不放寬

測試失敗時，預設是程式錯了，不是測試錯了。以下動作一律要先問使用者，並說明理由：

- 刪除測試、加上 skip，或把斷言改寬鬆（例如 `assertEquals` 改成 `assertNotNull`）
- 調大逾時、加上重試，讓不穩定的測試「比較常過」
- 把新的項目加進守門測試的例外清單

如果確定是測試寫錯了，要在回報裡明講「我改了測試，因為……」，不要混在實作修改裡一起帶過。

**為什麼：** 守門測試的例外清單本來是「已知缺口登記表」，例如「哪些寫入路由還沒有稽核紀錄」。如果為了讓 CI 變綠而把新路由塞進去，這份清單就從登記表變成了後門。所以團隊明文規定：不得為了讓測試變綠而修改例外清單。

## 不穩定的測試要找根因

間歇性失敗不要用重試或 skip 蓋掉，先找出根因：

- 先把單一測試檔重複跑 5～8 次。如果每次失敗的測試不一樣，多半是隨機資料造成的（例如亂數產生了 0），不是測試之間的順序污染。
- 檢查共用的狀態：file session、cache、時間（要凍結時間）、平行測試共用的資料庫。

**為什麼：** 一個間歇出現 302 的測試，最後查出兩個獨立的根因：file session 的回收機制在整套測試時隨機清掉 session，以及 factory 偶爾產生值為 0 的 ID，被當成「不存在」。加重試只會把這兩個 bug 一起藏起來。

## 結構性變更和行為性變更分開

重構（不改行為）和功能修改分成不同的 commit。重構的 commit 不應該需要改任何測試的預期結果。如果需要改，就代表它其實改到了行為。
