# 驗證迴圈：完成要有證據

## 動手前先定好「怎樣算完成」

每個任務開始前，先說出一個能跑出「通過」或「失敗」的檢查：要跑哪個測試、哪個指令、要看哪個畫面。說不出來，就先跟使用者確認驗收條件。

## 回報完成時附上證據

「已完成」的回報要包含**實際執行的指令**和**關鍵的輸出**，例如測試的通過數量、結束碼、截圖。「應該會過」不等於「已經過」：沒有證據就不算完成，要寫成「未驗證」。

git 和檔案操作也一樣：回報「已 commit」、「已撤銷」、「已刪除」之前，先用唯讀指令（`git log`、`git status`、`ls`）核對真實狀態，不要只憑對話記憶下結論。

## 檢查本身也可能說謊

**為什麼：** 以下都是「看起來綠了，其實沒驗到」的實例：

- commit hook 只檢查主工作區的 staged 檔，而改動在另一個 worktree。hook 看到「沒有改動」就直接略過，結果被當成測試通過。
- 背景跑整套測試時，腳本最後接了 `| tail`，結束碼被吃掉，失敗也回報 0。
- 單獨跑某個測試檔會過，整套一起跑卻因為記憶體不足而失敗。
- UI 改動只看了 HMR 的畫面，新的 CSS class 其實沒有被編譯進去。

**怎麼做：**

- 「略過」不等於「通過」。看到 skipped、0 tests、沒有輸出時，要追查原因。
- 結束碼要明確傳出去（`exit $rc`），不要在測試指令後面接會吃掉結束碼的管線。
- 影響範圍大的改動，要跑整套測試，不只跑相關的檔案。
- UI 改動要在真實的頁面上看過、截圖，不只看 build 有沒有成功。

## 需要強制時，交給 hook

「完成前一定要跑測試」如果是零例外的規則，就寫成 Stop hook 或 pre-commit hook，不要只寫在規則檔裡。規則檔是建議，hook 才能強制。
