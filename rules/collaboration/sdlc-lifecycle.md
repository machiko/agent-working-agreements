# 軟體開發生命週期：6 階段交付標準與品質閘門

在承接中大型功能開發（Feature）或複雜重構時，遵守 6 階段交付標準，避免跳步導致需求失真、品質脫節或生產事故。小型單檔微調、除錯或臨時查詢可簡化執行。

## 1. 規格階段（Spec & Alignment）：先對齊邊界，再動程式碼

動手前先明確定義「做什麼」與「不做什麼（Non-goals）」。若預期改動超過 3 個檔案，必須先出具計畫與驗收條件。

**為什麼：** 需求理解常有偏差。Agent 常在只讀了兩行模糊描述時，就一口氣修改十幾個檔案，最後發現完全脫離使用者原始意圖或破壞既有架構。

**怎麼做：**
- 整理「功能目標、影響範圍（檔案與 API）、資料表變更、非目標」清單。
- 提出具體的驗收條件（Given / When / Then 或操作預期）。
- 在使用者確認方向前，不要修改主要業務代碼。

## 2. 實作階段（Implementation）：原子提交與架構防呆

編寫代碼時維持原子性（Atomic），不將無關的重構或格式調整混入功能實作中，並嚴格遵守專案地雷守則。

**為什麼：** 混雜無關修改會讓 Code Review 困難重重；更常因為貪圖方便而吞掉錯誤（空 catch）、寫死機敏密鑰或漏掉租戶資料隔離。

**怎麼做：**
- 遵循防呆底線：禁止靜默吞噬錯誤、禁止在代碼放置明文密鑰、資料查詢嚴格約束租戶範圍。
- 一個 Commit 只做一件事，訊息採用規範化動詞（如 `feat:`、`fix:`、`refactor:`）。

## 3. 測試階段（Testing & Verification）：用真實綠燈說話

完成實作後，必須建立或執行對應的自動化測試，嚴格禁止跳過或偽造驗證。

**為什麼：** Agent 最常為了「看起來完成」而刪除報錯的斷言（Assertion）、隨意放寬比對條件，或聲稱「手動看過沒問題」卻從未真正執行。

**怎麼做：**
- 執行相關單元測試與整合測試，確認所有斷言實質通過。
- 禁止刪除或弱化既有測試以換取綠燈；測試失敗時追查代碼瑕疵，而非修改測試期望。
- 防範測試地雷：Mock 必須在 `afterEach` 清理，禁止使用靜態 `sleep` 等待非同步。

## 4. 驗收階段（Review & Acceptance）：主動出具自省審核與證據

提交驗收前，自我對照守則清查變更 Diff，並提供人類可重現的驗證步驟。

**為什麼：** 光靠「我做好了」無法建立信任，使用者必須花費倍增的時間去逐行檢查有沒有漏掉 edge case。

**怎麼做：**
- 執行自省審查（如 `/agreements:review` 或 `scripts/review.sh`），確認無遺留待辦或低級錯誤。
- 在對話或卡片中條列：測試執行結果摘要、重現步驟或 API 請求範例。
- 需要人類決策的事項（如權衡取捨、文案確認），明確標示在可見位置。

## 5. 合併階段（Merge & Integration）：檢查基底與守門防線

準備合併時，確認目標分支、消除衝突，並通過主動防護稽核。

**為什麼：** Agent 常沿用舊的終端狀態，把功能直接 commit 在別人的修復分支或直接 push 到主分支，導致部署污染或覆蓋他人成果。

**怎麼做：**
- 重新確認目前所在分支（`git branch --show-current`）與目標基底分支。
- 執行 `scripts/audit.sh` 確保未誤暫存 `.env*`、個資或全開放權限（`chmod 777`）。
- 走 Pull Request / Merge Request 流程，等候 CI 守門工作流全綠後才合併。

## 6. 上線階段（Release & Hygiene）：清理測試殘留與維護版本

發布或部署時，確保環境變數就緒、清除測試殘留，並留下清晰的版本軌跡。

**為什麼：** 上線時最常發生：測試用的 Mock Token 或假資料被帶上生產環境、新環境變數未在正式環境配置造成服務重啟失敗。

**怎麼做：**
- 確保所有新增的環境變數在生產環境皆有預設值或安全配置通知。
- 清理本機與容器中所有暫存的假資料、測試用 Dump 與暫存憑證。
- 更新 CHANGELOG 與語義化版號（SemVer），確保變更可被追溯。
