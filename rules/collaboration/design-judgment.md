# 設計判斷：一種顯式寫法，加上守門測試

## 不加隱含的機制層

一條橫切規則（稽核、權限、日誌）如果守門測試已經能強制覆蓋，就不要再疊 middleware、attribute、decorator 這類隱含機制。

**為什麼：** 曾經提出並實作過「attribute 宣告，加 middleware 猜測請求是否成功，再加請求層級的 context 自動寫稽核」的方案，被否決，理由是整體更複雜，卻沒有明顯改善。重新評估後確實如此：三種機制、隱含的控制流程、可能靜默只寫入一部分，換來的只是「看函式簽名就知道有記錄」。而守門測試本來就能提供這個結構保證。

小團隊重視的是「讀 controller 就看得出有沒有記錄」，以及「只有一種寫法」。隱含層在這種情境下是負債。

**怎麼做：**

- 提「業界成熟做法」之前，先分清楚這件事要的是「可以被機器檢查」還是「宣告式」。如果測試就能檢查，就不需要新機制。
- 想減少樣板程式碼，優先做型別安全的小 helper（例如參數吃 enum 的函式），不要做新機制。
- 如果要 5 條規則才能決定該用哪個 API，就是設計錯了，回到單一寫法。
- 真正能解決「程式碼散落各處」的是共用的 service 或事件層。做不到就誠實說暫時不做，不要用 middleware 模擬。

## 用守門測試鎖住慣例

慣例（「每個寫入路由都要記稽核」、「每個 enum 值都要有呼叫點」、「文件要列出所有 channel」）要寫成測試，在 CI 攔下遺漏。

- 例外清單要寫明原因，並把它當成「已知缺口登記表」，不是讓測試變綠的地方。不可以為了讓測試通過，把新的項目塞進例外清單。
- 文件如果被測試引用，就必須跟程式一起進版控，並且在同一個 PR 裡更新。

## 不要手寫會過期的清單

一份要對應上百個呼叫點的手寫清單一定會過期。改成把入口收斂到少數幾條路徑，用 enum 或程式碼本身當清單，再用測試保證文件和程式一致。

## 用增量分析取代每次全掃

大型 codebase 的分析結果存成一份基準文件，記下分析當時的 commit。下次只看 `git diff <基準 commit>..HEAD --stat` 有異動的檔案，更新對應段落和基準 commit。不要每個 session 都重掃整個專案。
