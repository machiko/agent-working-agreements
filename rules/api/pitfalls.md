# API 與整合契約地雷

> 跨語言通用的 API 設計、外部整合與系統通訊事故。格式：症狀 → 根因 → 怎麼做。

## 外部呼叫未設超時造成連鎖雪崩

- **症狀：** 第三方簡訊、發票、物流或外部 Webhook 響應變慢，本地後端的所有執行緒/Worker 迅速被吃滿，健康檢查逾時，所有其他不相干的 API 全部癱瘓。
- **根因：** 多數語言的 HTTP/RPC Client 預設超時是無窮等候（0 或數分鐘）。外部服務稍有延遲，並行請求就會迅速把本地工作資源與連線數全部耗盡。
- **怎麼做：** 所有外部網路請求一律顯式配置 `connectTimeout` 與 `readTimeout`（一般情境建議 connect <= 2s、read <= 5s）；關鍵外部相依必須具備熔斷（Circuit Breaker）或快速失敗（Fail-fast）機制，不可讓外部第三方卡死核心業務。

## 靜默吞噬錯誤 (Swallowing Exceptions)

- **症狀：** 生產環境某個功能無預警失效、訂單未建立、訊息未送出，但伺服器日誌全無任何異常，宛如進入黑洞無法除錯。
- **根因：** Agent 為了讓測試變綠或防止程式拋錯中斷，在呼叫外部服務或核心邏輯周圍加上了空的 `catch (Exception e) {}` 或 `except: pass`，把根因完全遮蔽。
- **怎麼做：** 嚴禁空 catch 區塊；捕捉例外時必須至少記錄具備 context 的 error log（包含原始錯誤堆疊與關鍵業務識別碼），或轉換為明確定義的領域例外往上層 Handler 傳遞。

## 破壞性欄位變更搞死用戶端

- **症狀：** 後端新版 API 一上線，尚未更新的 Mobile App、既有 SPA 頁面或合作夥伴微服務大批崩潰或 JSON 解析失敗。
- **根因：** 在既有 API 回應中直接刪除、重新命名欄位，或是變更欄位型別（例如數值 `id: 123` 改成字串 `id: "123"`），忽略了外部客戶端無法隨時熱更新。
- **怎麼做：** 已發布的 API 契約遵循「只增不改」原則；欄位淘汰必須走 Deprecation 流程（保留舊欄位並在文件註明棄用時程）；破壞性變更必須升級 API 版本（如 `/v1/` 到 `/v2/`）。

## 關鍵寫入缺乏冪等鍵造成重複扣款

- **症狀：** 使用者在網路不穩時連點兩次按鈕、或外部支付 Webhook 網路重送，系統重複扣除點數、產出兩張相同訂單或重複發放贈品。
- **根因：** 涉及資金、庫存等狀態變更的請求未要求傳入唯一冪等鍵（Idempotency-Key），伺服器將重試的請求視為獨立交易重複執行。
- **怎麼做：** 不可逆操作的端點強制要求 Header 傳入 `Idempotency-Key`；後端以快取或資料庫唯一索引（Unique Constraint）記錄處理狀態，重複 key 且已完成時直接回傳快取結果，處理中則阻擋並行操作。
