# Testing and mock pitfalls

> Cross-language testing incidents: mock leakage, static delays, dirty databases, over-mocking, and non-deterministic assertions.

### 1. Mock state leaking across tests (Mock State Leakage & Missing Reset)

When a test uses `jest.spyOn()`, `vi.mock()`, or `unittest.mock.patch`, clean up and restore after every test case. Never leave custom implementations or call counts behind.

**Why:**
AI agents often mock a global object (such as `fetch`, `axios`, or a system service) on the spot to fix the test at hand, then never clean it up in `afterEach` or the framework config. The test passes green when run alone, but when CI runs the whole suite in parallel, the leftover pollution makes other tests crash at random (flaky tests), which is extremely hard to track down.

**How:**
- Enable automatic restore in the test framework config (e.g. Vitest `restoreMocks: true`, Jest `restoreMocks: true`).
- When using `spyOn`, call `mockRestore()` or `vi.restoreAllMocks()` in `afterEach`.
- Know the difference between `mockClear()` (clears call counts only), `mockReset()` (clears counts and implementation), and `mockRestore()` (restores the original implementation).

```typescript
// ❌ Wrong: mocks a global object but never restores it after the test, polluting other tests
it('fetches user data', async () => {
  vi.spyOn(global, 'fetch').mockResolvedValue(new Response('{"id": 1}'));
  const res = await getUser(1);
  expect(res.id).toBe(1);
});

// ✅ Right: restore the original method after each test
afterEach(() => {
  vi.restoreAllMocks();
});
```

### 2. No static hard-coded delays in tests (Static `sleep` / `setTimeout`)

When testing async flows, queue processing, or event callbacks, never use static waits such as `sleep(1000)` or `time.sleep()`.

**Why:**
A static sleep usually passes on a developer's machine, but when the CI server is under heavy load or the CPU is throttled, the test times out and asserts before the background task finishes. Meanwhile, accumulated sleeps balloon a suite that should take seconds into tens of minutes.

**How:**
- Use the framework's conditional polling waits (e.g. `waitFor(() => expect(...))` in Vitest/Testing Library, `waitForResponse()` / `waitForSelector()` in Playwright).
- For logic that depends on time passing, use a virtual clock (fake timers: `vi.useFakeTimers()` / `jest.useFakeTimers()` / `freeze_gun`) to fast-forward instead of really waiting.

```typescript
// ❌ Wrong: hard-sleep 1 second waiting for an async callback
await new Promise(r => setTimeout(r, 1000));
expect(status.value).toBe('ready');

// ✅ Right: conditional polling passes as soon as the condition holds and fails only on timeout
await waitFor(() => {
  expect(status.value).toBe('ready');
}, { timeout: 2000 });
```

### 3. Integration tests must isolate database state (DB Transaction Rollback)

Any integration test that writes to the test database (INSERT/UPDATE/DELETE) must roll back its transaction automatically at the end or run in a randomized isolated environment. Never leave ghost data behind.

**Why:**
Test scripts generated by AI agents often write test users or orders straight into a real database without wrapping them in a rollback. When tests run sequentially or in parallel, later tests query the dirty data left by earlier ones, and the suite fails sporadically.

**How:**
- Always enable the framework's transaction rollback (e.g. Laravel `use RefreshDatabase;`, Django `TestCase`, Spring `@Transactional`).
- For databases without transaction support or multi-connection setups, explicitly truncate the relevant tables in `beforeEach` or `afterEach`, or isolate logically with a random UUID tenant ID.

### 4. Don't over-mock the private implementation of the unit under test (Over-mocking Implementation Details)

Tests should focus on the public API contract and boundary side effects of the system under test. Never mock the class's own internal private methods just to make a test pass.

**Why:**
To turn a test green, AI agents often replace all 3 private functions inside the object under test with fake data. The test then tests nothing but the mocks: after a future internal refactor the tests stay all green while production breaks outright.

**How:**
- **Mock only the outside world**: mock only boundary dependencies such as third-party HTTP APIs, external database connections, and cloud storage SDKs.
- Treat the internals of the unit under test as a black box and verify output state through inputs. If the internal logic is complex enough to need separate tests, refactor it into a new standalone service instead of mocking private methods.

---

### 5. Eliminate non-deterministic assertions from time and randomness (Non-Deterministic Tests)

Tests involving time, dates, or random numbers must pin the base time and the random seed. Never assert directly against a dynamic `new Date()` or `Math.random()`.

**Why:**
Tests that use the real system clock tend to blow up suddenly on "the last day of a month", "the instant the year rolls over", or "leap-year Feb 29". Randomized algorithms without a fixed seed throw on particular edge-case values and are hard to reproduce locally.

**How:**
- Pin the system base time before the test (e.g. `vi.setSystemTime(new Date('2026-01-01 12:00:00'))`).
- Use a deterministic pseudo-random generator with a fixed seed.
